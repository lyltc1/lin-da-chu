# 二维码点餐与订单回传

## 整体链路

```
App 发布菜单 ──► 仓库 menus/<menuId>/index.html ──► GitHub Pages
                                                        │
                                            朋友扫码打开静态菜单页
                                                        │
                                               选菜 → 生成订单码
                                                        │
                               App「扫码接单」◄── 扫朋友屏幕上的订单码
                                                        │
                                                  订单落本地 Room
```

**全链路没有后端**。菜单是 GitHub Pages 上的静态页，订单靠"扫码"这一次物理接触
完成回传。对家庭聚餐这种场景——朋友就在你面前——这反而比维护一台服务器更合适。

## 订单码格式

```
LC1|<menuId>|<tableNo>|<note>|<序号>:<份数>,...
```

示例：

```
LC1|m-8f3a2b|3|不要香菜|0:2,2:1,5:1
```

含义：菜单 `m-8f3a2b`，3 号桌，备注"不要香菜"，
第 1 道菜 2 份、第 3 道菜 1 份、第 6 道菜 1 份（序号从 0 开始）。

### 为什么只带序号不带菜名

二维码容量有限，中文按 UTF-8 编码每字要占 3 字节。菜单本身是固定快照，
菜品列表已经内嵌在页面里，用序号引用足矣。

码越简单，模块越大越稀疏，越容易扫——朋友举着手机给你扫的那几秒，
容错率就是体验。

### 前置条件

接单端必须能在本机查到这份菜单，才能把序号还原成菜名。因此发布时
**先落库、再推送**，这个顺序是硬的。若本机没有对应菜单，扫码会提示
"本机没有这份菜单，请先发布菜单再接单"。

### 转义

`tableNo` 与 `note` 中的 `|`、`,`、`:`、换行会被替换为空格，并截断到 60 字符，
避免破坏格式或让二维码过大。

## 静态菜单页

模板：`app/src/main/assets/menu_template.html`

- 单文件自包含，菜谱数据以 JSON 内嵌在 `<script>` 中（占位符 `__MENU_DATA__`），
  Pages 拿到即可渲染，无需构建步骤
- 移动端优先：卡片网格、封面懒加载、标签与难度时长
- 点卡片循环加减，单菜最多 9 份
- 桌号 + 备注 → 生成订单码 → 弹出二维码

### 二维码库的加载

页面通过 CDN 引入 `qrcode-generator`，并在加载失败时**优雅降级**：
不显示二维码，改为提示"可直接复制下方文本发给大厨"。

这样即使朋友处在无法访问 CDN 的网络环境，链路也不会断。

## 数据落库

订单写入 `orders` 表，明细写入 `order_item` 表，其中 `dishTitle` 是**冗余字段**——
下单之后菜谱可能被改名或删掉，订单要留住朋友当时看到的名字。

状态流转：`待接单 → 已接单 → 已完成`，或直接取消。

## 为什么不用 ML Kit

ML Kit 的条码识别依赖 Google Play services，在国内大量无 GMS 的设备上不可用。
ZXing 是纯 Java 实现，无额外运行时依赖，一个库同时覆盖"生成菜单码"和
"扫朋友订单码"两件事。
